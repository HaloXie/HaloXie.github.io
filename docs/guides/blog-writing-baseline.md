# 技术博客写作基线

这份基线记录一次针对本项目博客流程的自检结果。它回答两个问题：一篇文章怎样让读者快速抓住重点，怎样把复杂材料整理成可验证、可维护的页面。`AGENTS.md` 保留执行规则，本文件保留原因、模板和复盘证据。

## 先承认这次暴露的问题

本次 Git Flow 文章连续返工，根因不是缺少图或标题，而是起稿顺序错了：先写解释，再补案例、比较和图；读完后才发现主命题是“共享测试与差异化上线”，而不是某一个审查收益。结果出现了四类问题：

1. **主线没有先成立。** 读者必须读到后半段才知道分支、环境、tag 如何绑定。
2. **源材料被压成散文。** 画板里的回路、发布恢复和 Sprint 生命周期没有在第一版完整建模。
3. **信息层级失控。** 案例、命令、模型百科和免责声明挤在同一阅读路径。
4. **视觉服务于补丁。** Banner 和正文图职责不清，图表没有先回答“读者要做什么决定”。

这些是过程缺陷，不说明某个写作工具或某种 Git Flow 必然有问题。

## 可复用的文章骨架

```text
标题：矛盾 + 结果（避免只写主题名）
开头：一个具体场景，读者在 30 秒内知道冲突
Case 1 / Case 2：每个案例按 遇到什么 → 怎么处理 → 结果
核心模型：只定义理解主线所需的对象、关系和边界
总图：用一张图给出全貌；编号与速查表一致
关键差异：与主流方案按同一组维度对比
适用范围：适用、慎用、不适用各写清楚
按需展开：命令、恢复、变体、参考资料
```

主线验收只有五个问题：解决什么矛盾？有哪些对象？它们怎样关联？什么条件允许下一步？失败回到哪里？如果不展开附录仍答不出其中一项，就继续重排主线。

## 写作规则

- **先锁定一个核心命题。** 用“矛盾—做法—取舍”一句话写在草稿顶部；所有案例、图和比较都必须服务它。
- **按理解顺序减少切换。** 先场景，再最少概念，再总图和速查，最后才是例外与命令。段落一次只推进一个判断。
- **把对象关系说完整。** 对 Git 主题，至少分开写分支、环境、合并、部署、tag、验证和发布单位；不要用“合并到测试环境”这类混合说法。
- **案例要有动作和结果。** `Case 1 / Case 2` 不是装饰标题；每个案例都要说明冲突如何被流程吸收，以及什么仍需人工验收。
- **图表各司其职。** Banner 只表达命题；总图表达路径；表格用于查阅和比较；细图只解释高认知负担节点。不要用正文重复图上的每个节点。
- **主流对比要可追溯。** 引用一手资料，使用共同维度，写清典型场景和边界；不把“更适合本场景”写成“行业标准”。
- **少量重点高亮。** 加粗承重结论，不能把列表、代码和每个案例句子都高亮。发布前检查实际高亮命中，而不是只看 Markdown 标记。

| 读者问题 | 推荐表达 | 验收证据 |
| --- | --- | --- |
| 文章讲的是什么 | Banner 概念图 | 不含完整流程，不与首图重复 |

## 本次独立 agent 复核结论

本次安排了内容审读、语言审读和不同起点的模拟读者复核。共同意见不是“再加更多内容”，而是先修阅读路径：

- 内容审读指出，文章规则必须有边界；“保留全部原文”“比较所有主流方案”这类绝对句会把无关材料也变成硬要求。
- 语言审读指出，幕后说明、免责声明和“本文补充”式句子会打断作者口吻；应直接写实践、条件和结果。
- 模拟读者复述时最容易混淆三件事：分支与环境的绑定、合并与部署的区别、验证通过后由哪个版本发布。因此模板把这三组关系列为主线验收项。

这些反馈是 agent 模拟审读，不是实际读者调研；它们用于发现可复现的理解断点，不用于证明文章已经“写得好”。

| 来源 | 页面中可观察的做法 | 可迁移到本项目的规则 | 不应照搬的部分 |
| --- | --- | --- | --- |
| [Julia Evans](https://jvns.ca/) | 首页按时间列出短文章，标题和摘要直接说明读者能学到什么；很多文章用小例子解释一个概念 | 标题先给结果，开头先给可复述的例子；一篇文章只承担一个主要认知任务 | 她的漫画和短文节奏适合概念解释，不等于流程规范的完整性要求 |
| [Dan Luu](https://danluu.com/) | 长文围绕一个可争论的问题展开，常用数据、反例和链接支撑判断 | 把结论和证据绑定，主动写出反例与适用边界 | 长文长度和研究深度不适合所有博客主题；不能用篇幅代替结构 |
| [Stripe Engineering](https://stripe.com/blog/engineering) | 工程文章通常先交代背景与结果，再用分节、图表和实现细节支撑，末尾给出相关资料 | 首屏交代问题和收益，细节按层展开，参考资料可追溯 | 公司工程博客有团队编辑和产品背景，个人文章不应仿造其营销语气 |

## 独立试读的验收问法

让不同 agent 只读成稿，不看源文档，分别回答：

- 文章解决的矛盾是什么？
- 分支、环境、验证和发布的关系是什么？
- 正常路径从哪里开始，失败回到哪里？
- 与至少一种主流做法相比，改变了什么？

若两名读者在同一处答错，优先删重复内容或重排主线，再考虑增加解释。agent 反馈属于模拟试读证据，不能替代作者对实践语义的确认。

## 发布前最小检查单

- [ ] 已读 README、两篇站内范例和所有引用的源图；核心规则、前提、回路、边界有工作记录。
- [ ] 中文主线可独立阅读；英文、图中文字和 alt text 的语言状态明确。
- [ ] Banner 与正文图不同且各自承担明确任务；最终 WebP 已打开检查。
- [ ] 重点高亮命中核心结论；默认折叠不隐藏适用条件和放行条件。
- [ ] 运行 translations、series、reference-links、content-images、rendered-site 和 `git diff --check` 门禁；构建成功后再核对线上页面。
- [ ] 推送、构建、发布、线上验收四个状态分别记录，不能用“推送成功”代替发布证据。
